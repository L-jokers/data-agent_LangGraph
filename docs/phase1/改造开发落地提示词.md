

## 开发落地提示词

下面是一套可以直接在 Codex CLI 中逐步使用的流程。核心是：先只读分析，确认计划后分阶段实现，每阶段验收通过再继续。

### 第 0 步：准备工作区

  在开始前确认：

  - 智能问数系统改造技术开发方案.md 已保存并确认。
  - 你自己的未提交改动已保存，避免和实现 Agent 的修改混在一起。
  - 若希望实现与当前工作区隔离，先创建 Git 分支或独立 worktree；/clear 本身只清空对话，不隔离文件改动。
  - 暂时不要让 Agent 自动清空 MySQL、Qdrant 或 Elasticsearch 数据。

### 第 1 步：新开会话，只读熟悉项目和方案

  使用 /clear 后，发送：

  本会话负责按技术方案实现项目改造。请先阅读并理解：

    1. `智能问数系统改造技术开发方案.md`
    2. 项目中的 `AGENTS.md`（如存在）
    3. 与方案相关的现有代码、配置、Docker 文件和测试

  本轮只做只读分析，不修改任何文件、不运行会清理或修改数据的命令。

  请输出：

  - 方案各阶段与当前代码模块的对应关系
  - 当前实现与方案的差异
  - 分阶段实施计划，每阶段列出预计改动文件/模块
  - 每阶段的测试和验收方式
  - 方案中与当前代码不一致、存在歧义或需要我确认的事项
  - 数据库、Qdrant、ES 重建可能影响的资源范围

  不要开始编码。完成分析后等待我确认。

  审查它给出的分析。如果 Agent 误解了已确认口径或提出未经同意的数据清理，先让它修正计划。

### 第 2 步：确认计划并开始阶段一

  确认计划没有问题后，发送：

  我确认你提出的实施计划。现在只实现技术方案第 1 阶段：语义配置与元数据构建。

  开始前先简要说明：

  - 本阶段目标和明确不做的内容
  - 准备修改的文件
  - 是否涉及 MySQL、Qdrant、Elasticsearch 的数据清理或重建

  未经我明确确认，不得清空、删除或重建任何数据库、collection、index 或用户数据。不要执行 git commit。

  实现后：

  - 运行本阶段相关测试
  - 汇报改动文件、关键实现、测试命令和结果
  - 标记未完成事项和已知风险
  - 不要开始下一阶段，等待我验收

  验收重点：语义配置是否覆盖已确认模型；配置引用校验是否有效；数据构建是否来源一致；是否未经授权执行清理。

### 第 3 步：阶段一通过后，实现结构化意图和时间解析

  阶段一验收通过。现在只实现技术方案第 2 阶段：结构化查询意图和时间解析。

  必须遵守：

  - 指标口径按方案定义，不得自行更改
  - 业务时区为 UTC+8
  - 用户只提供月份但没有年份时必须澄清，不自动推断
  - 相对时间由 LLM 识别表达，再由确定性逻辑基于参考日期计算绝对范围
  - 澄清、拒绝属于正常终态，不得生成猜测 SQL 或执行查询
  - 本阶段不实现多轮会话
  - 不清理数据库或检索索引，不执行 git commit

  实现后运行相关单元测试，并汇报改动文件、测试结果、尚未覆盖的边界。不要进入下一阶段，等待验收。

  验收重点：结构化输出、解析失败处理、UTC+8 边界、相对时间范围、缺少年份时澄清，以及不支持问题不会进入 SQL 执行。

### 第 4 步：阶段二通过后，实现查询规划与语义校验

  阶段二验收通过。现在只实现技术方案第 3 阶段：查询规划与语义校验。

  要求：

  - 查询意图使用语义模型中的稳定 ID
  - 查询计划由系统根据语义配置生成，不接受 LLM 任意指定物理字段、JOIN 或 SQL 表达式
  - 校验数据集、指标、维度、关系路径、时间条件、聚合、过滤、排序和 limit
  - 月份过滤必须同时包含年份
  - 订单数使用 COUNT(DISTINCT order_id)
  - 平均每单购买件数按当前分组范围内的商品购买数量 / 订单数计算
  - 不支持或歧义的计划必须在 SQL 编译和执行前终止
  - 不实现多轮状态，不清理数据库或索引，不执行 git commit

  补充并运行规划器和语义校验测试，汇报文件、测试结果和剩余风险。等待我验收，不要开始下一阶段。

  验收重点：规划器是否从语义关系选择 JOIN；非法或歧义组合是否能被阻断；聚合和时间规则是否符合方案。

### 第 5 步：阶段三通过后，实现 SQL 编译、安全和 API 兼容

阶段三验收通过。现在只实现技术方案第 4 阶段：确定性 SQL 编译、安全和执行限制。

  要求：

  - 使用程序基于有效查询计划编译 SQL
  - 使用 MySQL 8 方言
  - 用户过滤值必须参数绑定
  - 表、字段、JOIN 和函数只能来自语义模型白名单
  - 自动添加或编译 LIMIT
  - 可添加 MySQL MAX_EXECUTION_TIME
  - 结果超过上限时截断，并明确返回截断元信息
  - 应用层设置查询超时
  - 扫描量精确限制暂列为已知限制，不要假称已实现
  - 使用 SQLGlot 对编译后的 SQL AST 做独立安全校验
  - 只允许单条 SELECT 查询及明确允许的查询表达式
  - 拒绝 INSERT、UPDATE、DELETE、DROP、ALTER、CREATE、TRUNCATE 和多语句
  - 拒绝白名单外的表、字段、函数和 JOIN
  - 校验 AST 中不存在绕过参数绑定的用户值
  - 默认删除当前 correct_sql → execute_sql 直通路径
  - SQL 执行失败默认返回稳定错误
  - 如果保留有限自动修正，修正结果必须重新经过：
      - 意图校验
      - 计划生成
      - 计划校验
      - SQL 编译
      - SQLGlot 安全校验
  - 不修改 API/SSE 契约，不清理数据库或索引，不执行 git commit

  预计改动范围：

  - 修改 pyproject.toml、uv.lock
  - 新增 app/compiler/
  - 新增 app/security/
  - 新增 sql_compiler.py
  - 新增 sqlglot_validator.py
  - 新增 query_limits.py
  - 修改：
      - app/repositories/mysql/dw/dw_mysql_repository.py
      - app/agent/nodes/generate_sql.py
      - app/agent/nodes/validate_sql.py
      - app/agent/nodes/correct_sql.py
      - app/agent/nodes/execute_sql.py
      - app/agent/graph.py

  运行以下测试并报告：

  - SQL 编译结构测试
  - MySQL 方言测试
  - 参数绑定测试
  - SQLGlot AST 测试
  - DML/DDL 拒绝测试
  - 多语句拒绝测试
  - 未授权表和字段拒绝测试
  - 注入值测试
  - MAX_EXECUTION_TIME 检查
  - LIMIT 检查
  - 结果截断测试
  - 应用超时测试
  - 数据库错误脱敏测试

  报告改动文件、测试结果、未实现项和已知限制。阶段五完成后停止，等待验收，不开始下一阶段。

  验收重点：SQL 与查询计划一致、用户值参数化、SQLGlot 安全校验、非只读语句拦截、白名单校验、超时和行数限制、结果截断，以及自动修正路径不会绕过完整校验。

  ———

  阶段四验收通过。现在只实现技术方案第 5 阶段：API/SSE 契约和回归验收。

  要求：

  - 在不改变 POST /api/query 基本请求格式的前提下完善 API/SSE 契约
  - 保持以下请求格式兼容：

  {
    "query": "查询 2025 年 1 月各大区的订单实付金额"
  }

  - SSE 事件顺序统一为：

  progress
  → sql
  → result / clarification / error
  → done

  - 支持以下终态：
      - success
      - needs_clarification
      - unsupported
      - error
  - 成功查询返回 SQL 和查询结果
  - 澄清场景返回澄清信息，不生成或执行猜测 SQL
  - 不支持场景返回明确原因，不伪造查询结果
  - 空结果使用：
      - done.status = success
      - result.rows = []
      - 明确表示查询成功但没有匹配数据
  - 结果超过限制时返回截断元信息
  - 错误信息脱敏
  - 不暴露候选评分
  - 不暴露数据库堆栈
  - 不暴露连接串、密码、API Key 等敏感信息
  - SQL 事件按需要脱敏参数
  - 不清理数据库或索引，不执行 git commit

  预计改动范围：

  - 修改：
      - app/api/schemas/query_schema.py
      - app/api/routers/query_router.py
      - app/services/query_service.py
  - 新增：
      - tests/api/
      - tests/integration/
      - tests/security/
      - tests/fixtures/
  - 根据需要更新 README.md

  运行以下测试并报告：

  - 原请求格式兼容测试
  - SSE 事件顺序测试
  - 成功终态测试
  - 澄清终态测试
  - 不支持终态测试
  - 安全错误终态测试
  - 空结果成功测试
  - 结果截断元信息测试
  - 错误脱敏测试
  - 阶段五 SQL 编译、安全和执行测试回归

  报告改动文件、测试结果、未实现项和已知限制。阶段六完成后停止，等待最终验收，不开始多轮查询阶段。

  验收重点：请求格式兼容、SSE 事件顺序正确、终态完整、SQL/结果正确返回、澄清和不支持场景不执行 SQL、空结果语义正确、截断信息完整，以及错误信息和敏感信息脱敏。

### 第 6 步：阶段四通过后，完善固定回归与结果核对

  阶段四验收通过。现在只实现技术方案第 5 阶段：固定问题集回归和结果正确性验证。

  请使用方案中的单轮案例和样本数据，补充必要的测试：

  - 案例一：多指标、时间、维度、排序
  - 四个指标的单独及合理组合查询
  - 缺年份月份必须澄清
  - UTC+8 相对时间解析
  - 未定义指标/维度、歧义、非法值的拒绝或澄清
  - SQL 安全边界
  - 使用独立核对 SQL 或固定预期值验证查询结果，而不只验证 SQL 可执行

  案例二和案例三仍属于未来多轮验收，不要求本阶段通过。不要实现多轮，不清理用户数据，不执行 git commit。

  运行相关测试并汇报覆盖情况、测试结果、未覆盖项和已知限制。等待最终验收。

  验收重点：结果数值是否独立核对；多轮案例是否正确标为后续范围；测试是否覆盖澄清、拒绝和安全路径。

### 第 7 步：要求 Agent 做最终自审，不要顺带扩展范围

  所有计划阶段已完成。现在请只做最终自审，不增加新功能、不重构无关代码、不执行数据清理、不提交代码。

  请逐条对照 `智能问数系统改造技术开发方案.md` 汇报：

  - 数据库及索引构建/回滚说明

  - 如何在本地复现构建、启动、测试和验收

  发现不符合方案的地方先列出，不要自行扩大修复范围。

### 第 8 步：带回当前会话验收

  把实现 Agent 的最终报告，以及必要的 diff、测试输出带回当前会话。我会按方案逐条检查；如果需要直接检查工作区，也可以在这个会话中进行只读代码审查。

### 一个重要约定

  每一阶段的提示词都要求 Agent 完成后暂停等待验收。不要一次性把所有阶段都授权给它，这样一旦前面语义模型或接口设计有偏差，后面的实现不会建立在错误假设上。
