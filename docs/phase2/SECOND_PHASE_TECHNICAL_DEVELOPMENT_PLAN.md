# 智能问数系统第二阶段改造技术开发方案

> 文档状态：已通过方案评审，作为第二阶段开发 Agent 的实施依据
>
> 方案范围：语义元数据外置、候选检索、时间理解、指标表达式编译、多轮澄清、有限修正及安全验收
>
> 开发约束：实施前检查工作区并保护既有改动；未经明确授权，不清理数据库、Qdrant、Elasticsearch 或 Docker volume，不轮换凭据、不提交代码。

## 1. 文档目的与使用方式

本文将第二阶段专题评审结论与已通过的实施任务基线合并，供实际开发 Agent 按任务顺序实施、测试和交付。本文中的“必须”“不得”属于实施约束；若实现中发现现有代码、数据库结构或依赖与本文不一致，应先报告差异和影响，不得静默改变已确认业务语义。

本文件是技术开发方案，不是对生产数据库、检索索引或配置执行破坏性操作的授权。涉及 DDL、数据迁移或索引写入时，开发 Agent 必须说明目标环境、脚本影响、回滚方式，并先确认操作资源。

## 2. 项目现状与第二阶段改造目标

### 2.1 当前实现观察

- `app/agent/nodes/parse_intent.py` 中存在指标和维度固定短语表及确定性短语分支；新增语义表达需要改代码或提示词。
- `app/time/parser.py` 仅覆盖有限固定时间表达；时间意图和规划时间模型主要表示单一连续范围。
- `app/agent/nodes/plan_query.py` 从项目目录固定路径加载 `conf/meta_config.yaml`，而不是从 MySQL 元数据库加载版本化运行时快照。
- `app/compiler/sql_compiler.py` 存在指标 ID 分支、固定表达式字典和固定字段引用扫描。
- `app/security/sqlglot_validator.py` 对参数名有固定 `p0` 至 `p5` 例外集合。
- 当前 API 请求仅包含 `query`，LangGraph state 没有会话恢复、澄清 ID、版本快照等多轮状态。
- 旧工作流中存在列、指标和值召回节点；Qdrant/ES 召回必须统一纳入主工作流，不能与新映射逻辑并行竞争。

上述为本方案编制时对当前工作区代码的检查结果。开发 Agent 开始实施时仍须重新核对代码和 Git 状态。

### 2.2 目标

1. 生产语义事实由外置、版本化的 MySQL 元数据库提供，不依赖部署包中的 YAML。
2. 通过统一候选检索扩大自然语言覆盖；候选始终回 MySQL 元数据校验，检索索引不成为事实源。
3. LLM 负责自然语言理解和缺失信息识别；时间运算、语义 ID 确认、规划、指标口径校验和安全检查由确定性逻辑负责。
4. 指标由结构化 JSON 表达式定义，普通指标增删改不要求新增指标级代码分支。
5. 支持多轮澄清、5 分钟会话过期、版本固定和乐观并发控制。
6. SQL 仍由确定性编译器生成，并经 SQLGlot 独立只读和白名单校验。
7. 仅允许有限、可证明不改变查询含义的结构化修正，修正后完整重跑可信链路。

## 3. 已确认的业务和设计基线

### 3.1 数据与语义

- MySQL 元数据库是语义元数据源；当前 MySQL 数仓继续提供业务事实数据。
- 元数据查询与业务数据查询保持隔离。
- MySQL 中的指标、维度、字段、关系、数据集、时间维度等均按 `version_id` 版本化。
- 每次查询使用一个 `SemanticModelSnapshot`；首次请求绑定唯一 active 版本，澄清恢复继续使用会话绑定版本。
- 不存在 active 版本时返回配置错误，不得使用 YAML 兜底。
- YAML 可以用于测试、示例或经过确认的初始化，但不是生产查询的语义事实源。

### 3.2 语义检索职责

| 组件 | 职责 |
|---|---|
| MySQL 元数据库 | 语义事实源、精确名称/别名匹配、候选最终校验、稳定 ID 与版本确认 |
| Elasticsearch | 对指标、维度、字段和值进行按类型隔离的 `lexical_search()`；可参考 `app/agent/nodes/recall_value.py` 现有实现 |
| Qdrant | `vector_search()` 向量召回；优先基于 `recall_column.py`、`recall_metric.py` 的现有实现扩展 |
| `SemanticCandidateRetriever` | 统一编排精确匹配、ES、必要时 Qdrant、合并去重、统一重排序、MySQL 回查和判定 |

索引是派生数据。ES/Qdrant 命中不能单独授权语义映射或 SQL 编译。索引候选必须可追溯到语义类型、稳定 ID、`version_id`，并回 MySQL 验证记录存在、版本相符且有效。

### 3.3 候选阈值及判定

统一重排序器输出 0–1 排序分数；ES 原始分数和 Qdrant 向量分数仅作为诊断信息及重排输入，不能直接横向比较或直接应用下表阈值。实现文档必须说明重排序计算方式、分数适用范围及局限，未经验证不得把排序分数宣称为经过统计校准的概率。已确认的目标策略如下：

| 语义类型 | 自动映射最低分 | Top1−Top2 最小分差 | 进入候选澄清最低分 |
|---|---:|---:|---:|
| 指标 | 0.92 | 0.15 | 0.65 |
| 维度 | 0.86 | 0.10 | 0.60 |
| 字段 | 0.90 | 0.12 | 0.65 |
| 过滤值 | 0.90 | 0.12 | 0.70 |

判定规则：

1. 规范化名称或已登记别名唯一精确命中时直接自动映射，不受分数阈值影响。
2. 冷启动默认关闭非精确自动映射；评分可靠性尚未验证时，非精确候选只用于排序和澄清。
3. 评分验证通过并显式开启后，非精确候选只有在 Top1 达到该类型自动阈值且 Top1/Top2 分差达标时才可自动映射。
4. 指标候选还必须通过元数据口径、状态、数据集和依赖校验。
5. 只有一个非精确候选时，没有 Top2，按不满足分差条件处理，进入澄清。
6. 未达到自动映射条件但达到澄清下限时，返回少量业务可读候选；不得要求用户理解物理表或字段。
7. 没有候选达到澄清下限时返回不支持。
8. 过滤值必须先确定维度，并只在该维度允许的值域内检索；分数不能代替维度确认。
9. 阈值和冷启动开关必须集中配置并可测试，不散落在节点代码。阈值调整需要回归测试，不自动沉淀或写回用户表达。

使用小规模人工构造的正反例验证排序和明显误匹配风险；不能将其描述为生产级统计校准。启用非精确自动映射须先验证评分并显式开启，启用后仍需通过上述阈值、分差和专项校验。

精确匹配规范化应限于无语义损失的文本规范化，例如空白、大小写、全/半角及标点规范化。不能通过宽泛文本变换把不同业务概念合并。

### 3.4 业务口径基线

- `fact_order` 当前粒度为一行一个订单。
- `order_count` 使用 `COUNT(DISTINCT fact_order.order_id)`。
- `paid_amount` 为 `SUM(fact_order.order_amount)`。
- `product_quantity` 为 `SUM(fact_order.order_quantity)`。
- 本项目 AOV 保留为“平均每单购买件数”，不是平均订单金额。
- GMV 未定义，不得自动映射到订单实付金额。
- “销量”在当前项目口径中是 `product_quantity` 的指标级别名，不写成节点特例；`order_quantity` 可同时保留字段级“销量”别名，但字段别名不能自动推导为指标定义。
- 业务时区 UTC+8；“本周”从周日开始、周六结束；支持不连续日期集合。

## 4. 目标工作流与节点职责

### 4.1 目标流程

```text
API request
  → load_or_create_session
  → bind_or_load_semantic_version
  → parse_intent
  → semantic_candidate_resolution
  → resolve_time
  → validate_intent_and_metric_requirements
      ├─ clarification → persist_session → SSE clarification/done
      ├─ unsupported → SSE unsupported/done
      └─ ready
          → load SemanticModelSnapshot
          → plan_query
          → validate_query_plan
          → generate_sql
          → validate_sql
              ├─ valid → execute_sql → persist terminal result
              ├─ eligible structural correction → correct once → replay trusted chain
              └─ security/semantic failure → terminate
```

具体节点可按现有 LangGraph 结构拆分或合并，但必须保持上述状态转换和信任边界。任何澄清/不支持/安全失败状态都不得流入 SQL 执行。

### 4.2 节点职责

| 节点/能力 | 职责 | 禁止事项 |
|---|---|---|
| 会话入口 | 创建/读取会话、校验过期和轮次状态、版本固定 | 覆盖已确认意图；绕过并发控制 |
| `parse_intent` | LLM 结构化提取用户意图 | 硬编码全量指标/维度；生成 SQL；自创语义 ID |
| `SemanticCandidateRetriever` | 按类型召回并校验候选 | 将 ES/Qdrant 分数当作语义事实 |
| `resolve_time` | 对结构化时间意图做 UTC+8 确定性计算 | 未识别表达后静默去掉时间条件 |
| 意图/指标校验 | 检查口径完整性、候选唯一性和所需定义 | 通过 LLM 猜测缺失口径 |
| `plan_query` | 从指定快照构造完整、稳定 ID 查询计划 | 读取项目 YAML 作为生产事实源 |
| 计划校验 | 校验 dataset、列、关系、表达式依赖、粒度及权限 | 接受未登记对象或不一致版本 |
| `generate_sql` | 从已校验计划/表达式树确定性编译 SQL | LLM 自由生成 SQL；拼接业务值 |
| `validate_sql` | SQLGlot AST 只读、对象、函数、JOIN、参数和结构校验 | 仅因 SQL 可解析就放行 |
| `correct_sql` | 最多一次的允许类别结构化修正及完整重跑 | 直接改 SQL 后绕过规划/校验 |
| `execute_sql` | 使用业务数仓连接执行已验证查询 | 使用元数据库连接执行事实查询 |

## 5. 版本化元数据与快照

### 5.1 版本表

至少维护：

```text
semantic_model_version
----------------------
version_id       主键/唯一版本标识
status           draft / active / archived
created_at
activated_at
description
```

采用单行当前语义版本指针表及事务化激活：指针表以固定单例键约束为至多一行，保存当前 active `version_id`；读取 active 版本只以指针为权威。激活事务锁定指针行，验证目标版本、元数据完整性及该版本检索索引验证成功记录，再更新指针并在同一事务维护版本表状态。不得保留两个独立的 active 事实源。没有指针、指向不存在版本或版本状态不一致时失败关闭；并发激活必须通过测试证明最终只有一个当前版本。ES/Qdrant 网络写入不得放入该 MySQL 激活事务。

### 5.2 版本化元数据

指标、维度、字段、关系、数据集、表、时间维度以及表达式/依赖定义都必须关联 `version_id`。复合唯一键、外键和查询条件应避免跨版本关联。检索索引 payload 至少包含：

```text
semantic_type
stable_id
version_id
display_name
aliases/description（按索引策略选择）
active/status
```

会话引用的旧版本必须保留到引用会话过期；本轮不要求建设在线双版本发布平台或自动回滚。

### 5.3 快照读取

`SemanticModelSnapshot` 应以一个 `version_id` 批量加载并验证完整关系。建议包含：

- 版本 ID；
- datasets、tables、columns、dimensions、metrics；
- relationships、time_dimensions；
- 表达式树及依赖关系；
- 元数据允许的业务能力和状态。

不得让 `parse_intent`、`plan_query`、编译器分别自行读取不受控版本。缓存若实现，键必须包含 `version_id`，并确保不可变或有明确失效策略。

构建工具允许通过显式指定的 `version_id` 加载并验证 draft 版本，用于构建派生索引；该能力不开放给正常查询入口。首次查询只选择 active 版本，澄清恢复只使用会话绑定版本。

### 5.4 派生检索索引构建与激活

初始化与查询是两条独立链路。初始化顺序固定为：审核后的 YAML 初始化数据 → `build_meta_knowledge.py` 写入 MySQL draft 版本 → 显式指定 `version_id` 构建 ES/Qdrant 索引 → 完整性及可检索性验证 → 显式激活。YAML 仅是一次性初始化输入；索引构建必须从 MySQL 指定版本读取语义定义，不得重新从 YAML 获取定义或恢复三库并行事实源。

针对固定语义版本及确定的索引构建配置，正常情况下构建一次。首次准备测试数据、新增版本、测试索引被清除、embedding 模型/向量维度/索引结构变化或构建失败重试时，才显式执行构建。应用启动、`hybrid_search()`、`lexical_search()`、`vector_search()` 不得创建索引、全量扫描元数据、生成全量 embedding、upsert 或隐式补写索引。向量检索为本次用户输入计算查询向量属于正常检索，不属于元数据初始化。

构建要求：

1. 复用并改造现有 ES/Qdrant repository 和 embedding 客户端；提供独立命令入口，显式指定 `version_id` 和目标资源，具体脚本名由开发 Agent 确定并记录。
2. ES 覆盖指标、维度、字段的词法文档及声明范围内的过滤值；Qdrant 构建相应语义实体的向量记录。明确每种语义类型、索引文本展开规则及各检索后端的覆盖范围，不得遗漏指标、维度和字段。
3. payload 至少包含 `semantic_type`、`stable_id`、`version_id`、被索引文本及必要展示信息；过滤值额外绑定维度。写入与检索均支持版本和类型隔离，过滤值检索还必须限制维度。
4. 过滤值按 MySQL 元数据声明的允许取值来源提取，必要时通过独立数仓连接读取；不得无约束扫描所有业务字段或把所有取值无限制写入索引。构建说明须列出取值范围及规模限制。
5. 使用确定性文档/point ID，标识覆盖版本、类型、实体和文本变体，避免重试重复。相同版本、内容和构建配置可幂等执行；配置发生变化时不得沿用旧的验证成功记录，须显式重建并重新验证。
6. 检查 embedding 失败、ES bulk 单项失败、Qdrant 写入失败和部分完成状态；失败不得报告成功，不得激活。成功分支和失败重试独立于 MySQL 初始化，不要求跨三库分布式事务。
7. 输出并持久记录可供激活检查的构建/验证结果，关联版本、元数据内容标识、索引配置、目标资源及 embedding 模型/维度；不记录凭据。成功记录必须与当前待激活内容和构建配置一致，不能仅靠一个历史成功标记放行。

完整性检查分两层：按 `(version_id, semantic_type, stable_id)` 比较预期实体集合与索引实体集合，检查缺失、额外实体及跨版本污染；再按明确的文本展开规则比较预期文档/point 的数量、ID 和必要 payload。名称、描述及别名可能产生多个向量，不能简单要求 MySQL 行数、ES 文档数和 Qdrant point 数相等。ES 写入完成后须确认数据已可被搜索，Qdrant 也须确认写入可检索；另外通过小规模正反例验证实际检索、版本/类型过滤及 MySQL 回查。记录数一致不代表召回质量已验证。

索引缺失、部分构建、验证失败或验证记录失效时，激活入口拒绝切换 active 指针。已激活版本运行中依赖暂时不可用时，可按第 13 节降级，但不得触发隐式初始化；初始化激活门禁与运行期降级不可混同。本轮不建设复杂在线发布、兼容双写或自动回滚平台。

**ES默认Index：data-agent-value**

**Qdrant默认Collection：data-agent-semantic**



## 6. 指标模型和表达式树

### 6.1 指标声明字段

指标至少需表达：

- 稳定 ID、业务名称、别名、描述、状态、版本；
- 指标类型及可加性分类（additive / semi-additive / non-additive）；
- 基础数据集、数据粒度、数据来源字段；
- 统计周期、业务限定、允许维度；
- 结构化表达式树和指标依赖；
- 结果类型、精度、单位；
- NULL 行为、除零行为；
- 若为窗口指标，窗口定义及适用范围。

不完整或相互矛盾的指标定义不得进入可查询状态。

### 6.2 表达式树能力

采用 JSON AST，不将自由 SQL 字符串直接执行。第一阶段能力至少覆盖已确认的：

- 列引用；
- 聚合；
- `COUNT DISTINCT`；
- 加减乘除；
- `NULLIF`；
- `CASE WHEN`；
- 条件聚合；
- 指标引用；
- 窗口表达式。

AST 节点需采用有版本的 schema，包含节点类型、参数类型和子节点约束。字段引用必须指向同版本已声明列；业务常量只能来自受控元数据参数或用户绑定参数，不能拼入 SQL 文本。

### 6.3 函数与操作符安全

- 普通指标增加只要求增加合法元数据。
- 新 SQL 函数或新表达式节点能力必须修改代码并经过安全评审。
- 允许函数、表达式节点、比较/逻辑运算符、过滤操作符由代码中的集中安全注册表控制。
- 元数据可以引用已批准能力，不能自行增加函数或运算符。
- SQL 参数值一律绑定，不得通过 AST 元数据拼接用户值。

过滤算子集合是有意保留的系统安全边界，不是指标级硬编码。所有支持的操作符都需有 AST 和参数化编译测试。

### 6.4 指标依赖规则

- 允许基础指标引用。
- 派生指标可以有限引用其他指标，最大依赖深度为 2。
- 开发实现必须在模型/代码文档中明确“深度”的计数口径，并测试边界：允许的最大深度通过，超过深度拒绝；本项目统一将深度定义为从目标指标沿依赖边到最深基础指标的边数。
- 检测环形依赖、未知依赖、版本不一致、粒度不兼容、重复聚合和非法阶段依赖。
- 窗口指标不得作为其他指标输入。
- 缺少来源、统计粒度、周期、业务限定或聚合方式时，由规则引擎生成缺项清单并触发用户澄清。

### 6.5 窗口规则

允许：

- 窗口函数作为最终输出字段；
- 窗口表达式引用已定义聚合表达式；
- `PARTITION BY` 已声明维度；
- `ORDER BY` 已声明指标或字段。

禁止：

- 窗口函数出现在 `WHERE`、`GROUP BY`、`JOIN ON`；
- 窗口函数作为其他指标输入；
- 自动构造需要额外子查询层的窗口过滤。

首版允许 `ROW_NUMBER`、`RANK`、`DENSE_RANK`、`LAG`、`LEAD`，以及经实现与兼容测试明确批准的聚合窗口函数；未列出的函数暂不支持，新增能力必须经过代码变更和安全评审。首版不开放任意窗口 frame。窗口表达式在聚合/分组结果之后编译为最终 SELECT 输出；排序使用已声明指标/维度的可编译表达式，不依赖未经验证的同层 SELECT 别名可见性。实际 MySQL 版本和 SQLGlot 兼容性须通过测试验证。

不满足上述边界的请求应澄清或返回不支持，不能自行改写为另一种统计含义。

## 7. 自然语言时间和离散日期

### 7.1 结构化职责

LLM 提取时间表达及其结构；确定性解析器计算日期。时间结果必须保留原表达和 UTC+8 语义，并支持：

- 单日；
- 连续日期闭区间；
- 多个离散日期；
- 多个区间（若由结构表达自然产生）。

### 7.2 业务规则

- 业务时区 UTC+8。
- 本周周日起、周六止。
- “最近 N 天”包含今天，按自然日闭区间。
- 无年份月份必须澄清。
- 无法解析或有歧义的时间不得静默忽略。
- 不支持表达和成功空结果必须区分。
- 离散日期去重、排序；重叠或相邻区间仅在不改变时间集合语义时合并。不同粒度混用且关系不明确时澄清，不猜测交集或并集。
- 每次查询最多 7 个离散日期、最多 5 个连续区间；超过任一上限时澄清，不静默截断。

### 7.3 SQL 编译

- 连续范围转换为参数化 `>=` / `<=` 日期边界。
- 离散日期转换为参数化 `IN` 条件或等价安全表达。
- 空日期集合不得生成无条件查询；应拒绝或澄清。
- 按最多 7 个离散日期、最多 5 个连续区间限制日期集合；超过上限时澄清，不生成无限参数。

## 8. 多轮会话与 API/SSE

### 8.1 存储选择

本轮使用 MySQL 应用会话表。Redis 不纳入本轮依赖；后续若会话量/延迟要求变化，可再评估 Redis 运行态缓存，但 MySQL 会话记录仍可保留作为一致性/审计来源。

本轮多轮范围仅为恢复待澄清请求，包括补充指标口径、时间、维度候选和必要筛选信息。不支持对已成功查询任意追加、替换、删除条件或基于上一轮结果追问；此类能力需另行确认范围。

会话逻辑过期为 5 分钟。读取时检查 `expires_at`；过期状态不得继续恢复。物理清理不是请求处理前置动作，不得通过清理数据库或 volume 实现过期策略；清理任务如需实施必须单独评估和授权。

### 8.2 会话记录建议字段

```text
session_id
status
original_query
current_query
clarification_id
turn_id / turn_number
state_version
semantic_model_version
pending_fields
query_intent_snapshot
query_plan_snapshot（按敏感性和必要性决定是否保存）
terminal_status / execution_marker（不保存完整结果）
created_at
updated_at
expires_at
completed_at
```

实现需避免在会话表保存凭据、完整数据库连接信息或不必要的敏感结果。表结构需给过期查询和会话查找建立合适索引。

### 8.3 API 契约

请求建议：

```json
{
  "session_id": "可选，首次请求省略",
  "query": "用户问题或针对澄清的回答"
}
```

- 首次请求无 `session_id` 时生成 ID 并通过 SSE 返回。
- 澄清回答使用同一 ID。
- 每轮返回当前状态。
- 继续使用 `text/event-stream`。

SSE 至少应提供：

```text
session（session_id、turn_id、当前状态）
progress
clarification（clarification_id、问题、候选选项/待补信息）
sql（只在 SQL 安全校验成功后发出）
result / unsupported / error
done（终态）
```

具体事件名称可兼容现有 API 契约，但事件顺序和终态必须稳定、测试覆盖。澄清不得发送 SQL 或执行 SQL。

### 8.4 乐观并发控制

- 同一 `clarification_id` 只允许一次有效状态迁移。
- 第一个成功提交的请求获得状态迁移权。
- 更新必须同时匹配 `session_id`、`clarification_id`、当前 `state_version` 和可接受状态；成功后递增版本。
- 更新行数为 0 时读取并返回当前状态，作为幂等响应。
- 同一澄清的后续请求不得覆盖已确认意图，不得重复执行 SQL 或重复写入完成状态。
- `session_id`/`clarification_id` 不匹配、会话过期、状态已终结均返回稳定业务状态。

不同回答并发到达时以第一个成功完成乐观锁状态迁移者为准；后续回答返回当前会话状态，不合并、不覆盖。

### 8.5 结果与失败窗口

本轮不持久化完整查询结果；结果仅通过 SSE 返回，会话记录只保存必要的状态、轮次、版本、澄清信息和完成标记。同一轮次已完成时，重复请求不得重新执行 SQL；如果结果无法重放，返回已完成状态并提示用户发起新查询。服务中断后若无法确定 SQL 是否已经执行，不自动重跑，返回中断或状态未知提示，由用户显式发起新请求。

实施时必须覆盖 SQL 已执行但完成状态或 SSE 未成功交付等失败窗口，并验证不重复执行；不能仅因存在乐观锁就认定端到端幂等已达成。结果重放能力不在本轮范围。

### 8.6 澄清恢复

恢复请求不得简单把新回答拼到原文后跳过校验。必须将补充回答纳入新一轮结构化意图解析，并重新执行候选确认、时间解析、指标定义校验、计划生成、计划校验、SQL 编译和 SQL 安全校验。整个会话始终使用初始绑定的 `semantic_model_version`。

## 9. SQL 编译、安全校验和有限修正

### 9.1 编译器

- 从 QueryPlan 和 JSON 表达式树生成 MySQL 8 参数化 SQL。
- 通过遍历 AST 收集表、列、函数、操作符、指标依赖和 JOIN 约束。
- 删除基于具体指标 ID 的编译分支和固定表达式字符串表。
- LIMIT、超时、只读策略仍由系统配置和代码控制。
- 继续保留结果截断探测逻辑，确保现有已验收行为不回退。

### 9.2 SQLGlot 校验

独立校验：

- 单条只读 `SELECT`；
- 表和列与计划/快照允许集合一致；
- JOIN 数量和条件与计划一致；
- 函数与表达式结构在代码能力注册表内；
- 不允许未展开 `*`；
- WHERE 中的值必须参数化；
- SQL 占位符集合与实际 params 键集合完全一致，不采用 `p0`–`p5` 固定例外；
- 窗口函数位置符合第 6.5 节；
- 执行时间、LIMIT 和结果规模限制仍生效。

### 9.3 有限修正

首版仅采用确定性规则进行修正，每次请求最多一次。LLM 可以重新提取结构化候选，但不能决定修复结果或自由改写 SQL。**允许类别限于可证明不改变查询语义的结构化修正**，例如：

- 唯一语义 ID/别名规范化；
- 输出字段名或 schema 字段名的结构修复；
- 对已明确表达但可能遗漏的意图重新提取候选，并由确定性规则验证；涉及指标、时间、筛选条件或粒度有歧义时必须澄清；
- `asc/desc` 等明确枚举格式规范化。

禁止自动修改指标口径、时间范围、离散/连续范围、过滤条件、分组粒度、GMV 等未定义口径；多个候选或用户意图有歧义必须澄清。

SQLGlot 判定的安全违规（DML/DDL、多语句、未授权表列、未批准函数、参数绕过等）直接拒绝，不触发模型“修到通过”。

任何修正后必须完整重跑：

```text
意图校验
→ 计划生成
→ 计划校验
→ SQL 编译
→ SQLGlot 安全校验
```

## 13. 数据迁移、索引和运行安全

- 当前 MySQL、Qdrant、Elasticsearch 均为测试环境。改造完成、全链路测试前，由用户清除残留测试数据，再按新结构重写；本轮无需长期兼容旧测试数据、旧索引或旧 payload，不建设兼容双写或旧索引迁移。该前提不授权开发 Agent 自行清理资源；首次初始化和索引构建前仍须确认目标环境、影响、校验及失败处置步骤。
- 首个版本先显式写入 MySQL draft 并审核，再从 MySQL 构建同版本 ES/Qdrant 索引、验证完整性与可检索性，通过后才显式激活；应用启动不得自动导入、构建索引或激活。该顺序取代“先激活再建索引”。
- 初始化需幂等保护：同版本同内容报告已存在且一致；同版本不同内容失败，不静默覆盖。版本 ID 由初始化操作显式指定，不固定为示例日期。
- 不得自动删除旧表、旧版本、Qdrant collection、ES index 或 Docker volume。
- Qdrant/ES 索引重建属于外部数据写入；须先确认具体 collection/index、写入策略、版本隔离和回滚方式。
- 检索索引缺失或不可用时，可以按定义的降级策略尝试 exact/ES/Qdrant 可用分支；不得把未校验的检索 payload 当作语义事实。若候选不足，应澄清或不支持。
- 凭据和连接信息保持敏感；测试日志、SSE 和错误响应不得输出秘密。
- 配置检查只核对键结构及读取路径，不输出凭据、完整连接串或 API Key。

## 14. 失败状态与可观测性

工作流需明确区分：

- `needs_clarification`：用户补充信息后可继续；
- `unsupported`：当前语义或表达不支持；
- `error`：内部依赖、配置、编译或运行错误；
- `success`：查询完成，可含空结果；
- `truncated`：受系统行数上限截断。

日志应包含可关联的 `session_id`、`turn_id`、`semantic_model_version`、节点名和失败类别，但不记录凭据、未脱敏敏感业务数据或不必要的用户原文。候选可观测信息仅用于诊断，不自动写回语义元数据。

## 17. 最终方案基线摘要

第二阶段以 MySQL 版本化元数据库为语义事实源，以 Elasticsearch 负责词法召回、Qdrant 负责向量召回，由 `SemanticCandidateRetriever` 统一组织候选并回 MySQL 校验。LLM 只承担自然语言理解和缺失信息识别；确定性组件负责时间、语义、规划、指标定义和 SQL 安全。指标表达式用 JSON AST 表示并受代码能力注册表约束。多轮澄清用 MySQL 会话表、5 分钟 TTL 和乐观锁实现，并固定首次绑定的语义版本。有限修正仅适用于不改变查询含义的结构化问题，且修正后重跑完整可信链路。

此基线是第二阶段开发 Agent 的实施依据；任何超出或偏离本文的产品行为、业务规则、资源写入或安全边界，须先经用户确认。
